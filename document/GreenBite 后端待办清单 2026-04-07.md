# GreenBite 后端待办清单

更新日期：2026-04-07  
用途：将后端缺口整理为可执行的开发任务，便于分工、排期和验收。

---

## 1. P0：当前最优先

这些任务优先级最高，直接影响前端完整联调、MVP 演示闭环和关键业务正确性。

### P0-1 新增订单查询接口

任务：

- 新增 `GET /orders/{id}`
- 新增 `GET /orders?userId=...`

目标：

- 支持前端“我的订单”页面从后端读取真实数据
- 支持查看单个订单详情

建议返回字段：

- `orderId`
- `userId`
- `status`
- `createdAt`
- `items`
- `totalCalories`
- `totalProtein`

验收标准：

- 用户可查询自己的订单
- staff/admin 可按权限查看对应订单
- 前端不再依赖本地缓存展示订单历史

---

### P0-2 新增食材查询接口

任务：

- 新增 `GET /ingredients`
- 新增 `GET /ingredients/{id}`

目标：

- 支持员工端真实展示食材与库存信息

建议返回字段：

- `ingredientId`
- `name`
- `allergens`
- `currentQty_g`
- `expiryDate`
- `stockStatus`

验收标准：

- 员工管理页面能从后端拉取完整食材列表
- 可展示库存状态、高库存/临期信息

---

### P0-3 补全菜品详情字段

任务：

- 在 `GET /meals/{id}` 响应中补充 `sustainabilityScore`
- 为菜品增加展示图片能力
- 支持前端通过文件上传而不是手填 URL

目标：

- 保证菜品详情页只用一个详情接口即可完整渲染
- 让员工上传菜品图片后能够真正写入后端并跨设备生效

验收标准：

- 菜品详情接口返回：
  - `mealId`
  - `name`
  - `description`
  - `calories`
  - `protein`
  - `sustainabilityScore`
  - `imageUrl`
  - `ingredients`
  - `tags`

补充要求：

- `GET /meals` 返回中也应包含 `imageUrl`
- 菜品图片应通过文件上传接口获得 `imageUrl`
- 前端不再依赖本地 data URL 缓存保存图片

建议后端补充：

- 新增上传接口：`POST /uploads/images`
- 或新增菜品图片接口：`POST /meals/{id}/image`

建议请求格式：

- `multipart/form-data`
- 文件字段名建议统一为 `file`

建议返回格式：

```json
{
  "imageUrl": "/uploads/meals/meal-1-cover.jpg"
}
```

建议同时补充：

- 文件类型校验，仅允许图片
- 文件大小限制
- 静态资源访问路径
- 替换旧图时的清理策略

---

### P0-4 修正 dashboard 统计口径

任务：

- 检查并修正 `DashboardMapper.topMeals()` 的 SQL 统计逻辑
- 确保只统计 `confirmed` 订单

目标：

- 避免将未确认或已取消订单误计入 dashboard

验收标准：

- 用测试数据验证：
  - pending 订单不计入
  - cancelled 订单不计入
  - confirmed 订单才计入

---

### P0-5 强化订单确认的库存并发安全

任务：

- 改造 `confirmOrder()` 库存检查与扣减逻辑
- 增加并发保护

可选方案：

- 悲观锁
- 乐观锁
- SQL 原子更新

目标：

- 避免多个订单同时确认时超卖

验收标准：

- 并发测试下不会出现库存被扣成负数
- 库存不足时返回明确冲突错误

---

## 2. P1：强烈建议紧接着做

这些任务不一定立刻阻塞 MVP，但会明显影响接口可用性、系统稳定性和后续扩展。

### P1-1 补 DTO 与参数校验

任务：

- 将当前 `Map<String, Object>` 请求体改为 DTO
- 为关键字段增加 `@Valid` 校验

优先覆盖接口：

- 登录、注册
- 用户更新
- 偏好更新
- 菜品增改
- 食材增改
- 订单创建
- 库存更新

验收标准：

- 非法参数返回明确 400
- 不再依赖运行时类型转换兜底

---

### P1-2 完善 dashboard 返回结构

任务：

- 扩展 `GET /dashboard` 返回字段，覆盖需求文档中的管理员指标

建议增加：

- `topRecommendedMeals`
- `topSelectedMeals`
- `highStockIngredients`
- `nearExpiryIngredients`
- `mealSustainabilityStats`
- `lowCarbonSelectionCount`

验收标准：

- 前端 dashboard 不需要大量自行推导
- 可直接映射需求文档中的管理员页面

---

### P1-3 增强报告接口

任务：

- 丰富 `GET /reports/sustainability` 的返回内容

建议增加：

- 更可读的 summary
- 统计说明
- 关键结论字段

可选增强：

- 支持时间范围参数

验收标准：

- 报告接口不只是 dashboard 的简单转发

---

### P1-4 密码哈希化

任务：

- 将明文密码改为 BCrypt 存储
- 登录改为哈希比对

目标：

- 消除最明显的安全短板

验收标准：

- 数据库中不再保存明文密码
- 现有测试账号仍可登录

---

### P1-5 增加错误日志和关键业务日志

任务：

- 在异常处理处记录错误日志
- 对关键业务动作增加日志

优先日志点：

- 登录失败
- 下单
- 订单确认
- 订单取消
- 库存更新
- 管理员访问报告

验收标准：

- 出现错误时可从日志快速定位

---

## 3. P2：中期改进

这些任务对系统质量和可维护性很重要，但优先级低于 P0/P1。

建议增加：

- `calories`
- `protein`
- `sustainabilityScore`
- 更细的推荐理由
- 可选的分项得分

验收标准：

- 前端推荐页不需要额外拼很多数据

---

### P2-2 增加推荐分项解释

任务：

- 返回推荐计算分解结果

建议字段：

- `healthScore`
- `preferenceScore`
- `sustainabilityScorePart`
- `stockPriorityScore`

目标：

- 提高可解释性，方便演示和调试

---

### P2-3 优化库存模型

任务：

- 决定库存到底采用“单记录模式”还是“真正批次模式”

如果保留批次模式，需要做：

- 多批次查询
- 临期优先消耗
- 批次级扣减

如果不做批次模式，需要做：

- 简化表设计和代码逻辑保持一致

验收标准：

- 数据模型和业务逻辑不再矛盾

---

### P2-4 增加列表筛选/分页能力

任务：

- 为列表型接口增加分页、过滤、搜索参数

优先考虑：

- meals
- ingredients
- orders

---

### P2-5 完善异常码体系

任务：

- 统一业务错误码
- 区分参数错误、权限错误、资源不存在、状态冲突、库存不足等场景

目标：

- 便于前端精细化处理错误
